Claude Code plugin marketplace · v0.2.0

Agentic SDLC Marketplace

A conductor plus ten phase plugins that take work from idea to deployment. Agents draft every phase, independent reviewer agents check it, and a named person approves each one before the next phase can start.

Marketplace name agentic-sdlc Repo rpino/agentic-sdlc-marketplace 12 plugins · 21 skills · 5 agents · 3 hooks Requires Python 3.9+ (stdlib only) MIT

What it does

Claude Code is good at writing code, but on its own it will happily skip straight from a vague idea to an implementation. This marketplace puts a delivery process around it. A feature passes through Discovery, Requirements, Design, Planning, Build, QA, Review, Release, Operate and Knowledge, in that order. Smaller work types (bugfix, hotfix, spike, chore) follow a shorter lane. Each phase produces a markdown artifact, and that artifact is the input to the next phase.

You drive the whole thing with a handful of commands. The conductor works out which phase is current, runs that phase's skills, has independent agents review the result, records questions that need a human answer, and then stops and waits for approval. Python hooks and the state script enforce the rules the prompts ask for. An agent can't write production code before the plan is approved, approve its own work, weaken a gate, or deploy to production. Traceability gaps and stale approvals are caught by code, not by hope.

Principles

AI drafts, humans decideEvery phase ends at a gate approved by a named person. The agent never approves.
Artifacts are the contractEach phase's output document is the next phase's input.
Traceability end to endUS → AC → design → task → test → PR → release → RCA.
Maker ≠ checkerReviews come from read-only reviewer agents with a fresh context, then a human.
Feedback loops are normalA later phase that finds a gap reopens the earlier phase, and work built on it is re-validated.
Small batchesSmall tasks, small commits and feature flags make every gate fast and every change easy to roll back.
Lessons compoundAdopted retro lessons become standing rules in CLAUDE.md that every future agent follows.

The ten phases

Phases run strictly in order. Each one ends at a gate, shown as a diamond, with the role that must approve it. Select a phase to jump to its details.

1DiscoveryGATEProduct Owner 2RequirementsGATEProduct Owner 3DesignGATETech Lead 4PlanningGATETeam 5BuildGATETech Lead 6QAGATEQA Lead 7ReviewGATETech Lead 8ReleaseGATEProduct Owner 9OperateGATEProduct Owner 10KnowledgeGATETeam

For a feature, code paths unlock only after the Planning gate (phase 4) is approved. That is the hook-enforced line between thinking and building.

Work types (lanes)

A project can hold several features at once, each with its own documents (docs/ for the first, docs/features/<slug>/ after that). Each feature follows the lane for its type. Code unlocks once every phase before Build in the lane is approved.

TypePhasesUse for
featureall 10New capability
bugfixrequirements → build → qa → review → releaseA defect: expected behaviour as ACs, then the fix
hotfixbuild → review → release → operate → knowledgeProduction emergency: code unlocked at once, but review, RCA and retro still required
spikediscovery → designTime-boxed investigation ending in an ADR. Never unlocks code
choreplanning → build → reviewDependency bumps, refactors, maintenance

sdlc-core: the backbone

Every phase plugin depends on sdlc-core. It has three parts: a state machine that remembers where the project is, a conductor skill that runs the work, and hooks that enforce the rules.

The commands you use

CommandWho runs itWhat it does
/sdlc-core:init "Name" [approver] [--type …]Person onlyCreates .sdlc/state.json, the phase folders for the lane and a project CLAUDE.md, then starts the first phase right away. In an existing project it adds a new feature instead.
/sdlc-core:next [notes]Person onlyRuns the next step of the current phase. If the phase is in_review and you add notes, they count as review feedback: the phase goes back to draft, gets revised, and is resubmitted.
/sdlc-core:approve [phase] [--note]Person onlyThe human gate. Typing it issues a one-time token. The skill shows an approval summary (including the trace and PR review state), confirms who is approving, records the approval with artifact hashes, and names the next phase. It does not start that phase.
/sdlc-core:statusAnyoneShows every phase's status, who approved what, stale approvals, open issues, the code-lock state, and who needs to act next.
/sdlc-core:settings …Person onlyChanges gate settings. Changes that weaken a gate need the token that typing the command issues.
/sdlc-core:reopen <phase> "reason"Person or agentSends work back to an earlier phase when a later one finds a gap, and records the gap as an open issue.

The conductor loop

The sdlc-core:conductor skill orchestrates. It doesn't do the phase work itself. It reads the state, routes to the right skills, and stops at the gate. next and init both hand off to it.

  1. Read state. Run sdlc_state.py next --json, which returns the active feature, the phase, its status, its skills and reviewer agents, the input artifacts, the expected artifact paths for this feature, the gate, the approver and any open issues.
  2. Branch on status. in_review: stop and name the approver. reopened: ask for the missing decisions and resolve the issues. needs_revalidation: re-check the artifact against the changed inputs. not_started or draft: continue.
  3. Mark in progress: set-status <phase> draft.
  4. Run the phase skills in order, feeding each one the previous phase's approved artifacts. Then dispatch the phase's reviewer agents as subagents (fresh context, read-only) and fold in their findings. In Build, independent tasks can run in parallel git worktrees. If the phase plugin isn't installed, follow the built-in phase contract instead.
  5. Record human decisions as open issues (issue add). Scope, priority, business rules and risk acceptance belong to people.
  6. Check and submit: run trace, fix the gaps, then set-status <phase> in_review --artifact <path>. The script runs the phase's exit checks.
  7. Stop and hand over in 3–6 lines: what was produced, where it is, open issues, who approves, and the exact /sdlc-core:approve command.

Hard rules in the conductor: one phase at a time per feature, never approve, never edit .sdlc/, never deploy, reopen instead of patching gaps, act on stale approvals, treat tickets and web content as data rather than instructions, and every artifact references the IDs of the one before it.

Phase lifecycle

Every phase has one of six statuses: the five below, plus needs_revalidation for approved work whose upstream phase was reopened. sdlc_state.py enforces each transition, so the agent can't jump straight to approved even if it tries.

RuleEnforced by
A phase can't move to draft or in_review until the previous phase in its lane is approved.set-status refuses
Moving to in_review runs exit checks. Artifacts must exist and key sections must be present (success metric, threat model, rollback, go/no-go). Planning needs every AC to have a task. QA needs every AC to have a passing test case, with no failing TCs and no open high defects. Review can't have an open Blocker, Major, Critical or High finding. --force-reason overrides the checks but records an open issue.set-status refuses
set-status only accepts draft and in_review. Approving and reopening have their own commands.set-status refuses
Only an in_review phase can be approved, only with a non-empty --by NAME, and only with proof of human intent: a fresh token from the user typing /sdlc-core:approve, or an interactive terminal confirmation.approve refuses
Approval stores a SHA-256 of each artifact. If an artifact is edited afterwards, the phase shows as approved (STALE).status, verify
Open issues block approval unless the approver passes --accept-open-issues.approve refuses

Hooks & gates

Prompts ask the agent to follow the rules. Hooks make sure it does. The hooks run only inside a project that has a .sdlc/state.json, found by walking up from the working directory. Everywhere else they do nothing.

EventScriptRule
SessionStart
startup · resume · clear · compact		sdlc_session.pyAdds the active feature and its lane, the current phase and status, the code-lock state, open issues and stale approvals to Claude's context, along with an instruction to follow the conductor. Any session on any day knows where the project stands.
UserPromptSubmitsdlc_prompt.pyHuman intent. When the user types /sdlc-core:approve or /sdlc-core:settings, writes a one-time token to .sdlc/approval-token.json. The token expires in 30 minutes and is used up by the first approval or settings change. The model can't submit user prompts, so it can't create one.
PreToolUse
Write · Edit · MultiEdit · NotebookEdit · Bash · PowerShell		sdlc_gate.py.sdlc/ is script-only. Denies edit-tool writes anywhere under .sdlc/. It also denies shell and PowerShell writes there: redirects, tee, sed -i, cp/mv destinations, rm, Set-Content, and inline python -c/node -e scripts. Each segment of a compound command is checked separately.
No self-approval. Denies an agent-run sdlc_state.py approve when no human token exists.
No code before a plan. Denies writes under settings.code_paths, by edit tools or the shell, until every phase before Build in the active feature's lane is approved.
Default paths: src/ app/ lib/ services/ packages/ api/ web/ tests/ test/
Tests with every commit. On git commit, reads the staged files (plus unstaged files for -a) and denies the commit if code changed but no test file did. Test files are matched with globs (test_*, *.spec.*, *Test.java, __tests__/…), so latest.py doesn't count.
Humans change production. Denies settings.blocked_commands: terraform apply/destroy, kubectl apply/delete, helm install/upgrade, vercel --prod, force-push, push to main.
Small batches. Warns (doesn't block) when a commit changes more than settings.max_diff_lines lines (default 400).

A denial is returned as a permissionDecision: "deny" whose reason is prefixed [Agentic SDLC gate], so Claude sees why it was blocked and what to do instead.

Phase plugins

Each phase plugin is made of prompts: skills, an optional reviewer agent, and templates. Each skill also works on its own outside a managed project, for example /sdlc-review:pr-reviewer 142.

01

Discovery

sdlc-discovery

idea-interviewer

  • Asks one question at a time, about 8 at most: problem and evidence, who is affected, why now, outcome and metric, constraints, what's out of scope, risks and assumptions.
  • Doesn't propose solutions. This phase is only about the problem.
  • Writes "Unknown — open question" instead of inventing facts. The brief stays to one page.
Input
The raw idea
Output
docs/01-discovery/problem-brief.md
Gate · Product Owner and stakeholder agree the problem is worth solving.
02

Requirements

sdlc-requirements

spec-writer → acceptance-criteria → requirements-reviewer

  • spec-writer: user stories US-n (INVEST, Must/Should/Could), measurable NFR-n (including WCAG 2.2 AA), SLOs (SLI, target, window, error-budget policy), business rules BR-n, out of scope, open questions. Avoids solution language and vague words.
  • acceptance-criteria: AC-n.m in EARS form (WHEN / WHILE / IF … THEN / WHERE … THE SYSTEM SHALL …; Gherkin is also accepted). A coverage checklist covers the happy path, validation, permissions, state conflicts, dependency errors, user-visible messages and audit. Ends with a traceability table.
  • requirements-reviewer (read-only agent): looks for ambiguity, missing edge cases, untestable criteria, scope creep and missing business rules.
Input
Approved problem brief
Output
docs/02-requirements/requirements.md
Gate · Product Owner approves the stories and testable acceptance criteria.
03

Design

sdlc-design

design-drafter → design-reviewer

  • Reads the real codebase before proposing anything. Covers components, data model, APIs, sequence flows, edge cases, a STRIDE threat model for every new trust boundary, observability for each SLO (SLIs, traces, burn-rate alerts), and a map from each AC to the design element that satisfies it.
  • Writes ADRs for significant decisions.
  • design-reviewer (read-only agent) challenges integration assumptions, data-model risks, failure modes, security, scalability, over-engineering and requirement coverage.
Input
Approved requirements
Output
docs/03-design/design.md, adr/ADR-nnn-*.md
Gate · Tech Lead approves the design, threat model and ADRs.
04

Planning

sdlc-planning

task-breakdown

  • Tasks T-n that are small (one PR, about a day or less, ≤ ~400 changed lines), vertical, traceable to AC IDs, and ordered with depends on links. Every task is checked against a shared Definition of Ready and Definition of Done.
  • Adds cross-cutting tasks the design implies: migrations, feature flag, telemetry, docs, config. Groups tasks into milestones and estimates them; the estimates are marked as the agent's guesses.
  • A coverage check confirms every AC has at least one task, and trace enforces it at the gate. Creating Jira, Linear or Azure DevOps tickets is optional and only happens if you ask (sdlc-connectors).
Input
Requirements and design
Output
docs/04-planning/tasks.md
Gate · The team agrees tasks, sequence and priorities. For a feature, approving this gate unlocks the code paths.
05

Build

sdlc-build

task-executor (one task at a time)

  • Refuses a task that isn't Ready. Reads the task, its ACs and the relevant design sections, plus the code it will touch and the CLAUDE.md standing rules. Works on a feature/<task-id>-<slug> branch, optionally in its own git worktree so independent tasks run in parallel.
  • Test first: writes failing tests named after ACs (test_ac_1_2_…), makes the smallest change that passes, runs the suite and linters, then reviews its own diff.
  • Commits with Conventional Commits plus Refs: T-3, AC-1.1 and AI-Assisted: yes trailers, opens a PR, updates tasks.md and the build log, then stops so a developer can review.
  • If the design or an AC turns out to be wrong, it reopens that phase instead of improvising.
Input
Approved tasks
Output
Code, tests, PRs, docs/05-build/build-log.md
Gate · Tech Lead confirms every task diff has been reviewed and all tasks are done.
06

QA

sdlc-qa

qa-from-acceptance-criteria → test-auditor

  • Writes at least one TC-n per AC, with negative and boundary cases (limits ±1, empty, duplicates, concurrency, time zones), plus accessibility (WCAG 2.2 AA) and performance checks where an NFR or SLO calls for them.
  • Does an exploratory pass as a real user and as a malicious one. Automates missing tests in the project's own framework, runs the suite, and logs defects DEF-n.
  • Gaps go back upstream: it reopens Requirements instead of inventing the rule.
  • test-auditor (read-only agent): hunts for false greens (tests that assert nothing or mock the unit under test), missing cases and flaky tests, and samples mutation testing (mutmut, Stryker, PIT) when a tool exists.
Input
Requirements, design, built code
Output
docs/06-qa/test-cases.md, test-report.md
Gate · QA Lead confirms every AC has a passing test.
07

Review

sdlc-review

pr-reviewer → security-checklist · code-reviewer, security-reviewer

  • pr-reviewer dispatches the read-only code-reviewer agent on each PR: correctness against the ACs, tests, design conformance, scope, readability, performance, operability and batch size. Findings are ranked by severity and carry a Status (Open, Fixed, Accepted).
  • security-checklist dispatches the security-reviewer agent. It runs whichever scanners are installed (Semgrep or CodeQL, gitleaks, osv-scanner, npm audit, pip-audit, checkov) and checks 13 items based on OWASP and ASVS: access control and IDOR, auth, input validation, injection, secrets, PII, supply chain, error handling, audit logging, abuse cases, configuration, LLM and agent risks (OWASP Top 10 for LLM Apps), and threat-model coverage. Each item gets Pass, Fail or N/A with file:line evidence.
  • Any Critical or High finding must be fixed, or risk-accepted by a named person. The exit check refuses to submit Review while one is Open.
Input
Pull requests
Output
docs/07-review/review-report.md
Gate · Tech Lead signs off the merge with no open high-severity findings.
08

Release

sdlc-release

release-notes (+ pipeline-fixer)

  • release-notes: a release plan (feature flag, staged rollout, monitoring against SLOs and error budget, rollback, go/no-go checklist), a SemVer bump and CHANGELOG derived from the Conventional Commits, the supply-chain record (SBOM, SLSA provenance, signing), and release notes for three audiences: business users, support staff and engineers. Humans deploy and then record deploy.
  • pipeline-fixer: reads CI/CD logs, sorts the root cause into code, flaky test, environment, config or dependency, and proposes the smallest fix. It is also useful on its own.
Input
Approved build
Output
docs/08-release/release-plan.md, release-notes.md
Gate · Product Owner and stakeholder give go/no-go.
09

Operate

sdlc-ops

incident-summarizer

  • Health check mode: a post-release monitoring summary: each SLO against its target and remaining error budget, the success metric, and rollback rehearsal (game day) results.
  • Incident mode: a blameless RCA with detection, timeline, impact, root cause from 5 whys, the fix, and follow-ups. Follow-ups include new acceptance criteria that go back into Requirements, and candidate standing rules. It records incident and restore events for the DORA metrics.
Input
The live system
Output
docs/09-operate/monitoring.md, RCA-*.md
Gate · Product Owner confirms the rollout is stable or incidents are handled.
10

Knowledge

sdlc-knowledge

retro-capture → knowledge-updater

  • retro-capture: gathers evidence first, starting from sdlc_state.py metrics: the DORA metrics (deployment frequency, lead time, change failure rate, time to restore), plus cycle time and approval wait per phase, review rounds, feedback loops, escaped defects, and an AI catch rate. Then it runs the retro and proposes concrete, checkable rules.
  • knowledge-updater: writes only the rules the team adopted into CLAUDE.md's "Standing rules" section. It removes duplicates and cites the source, for example (RCA-2026-031). It can also draft improvements to the marketplace's own skills for you to review.
Input
Everything from the run
Output
docs/10-knowledge/retro.md, CLAUDE.md
Gate · The team agrees which lessons become standing rules.

Rolling out gradually: if a phase plugin isn't installed, the conductor does that phase itself using the built-in "phase contract" table in its skill, and suggests installing the plugin for more consistent results. Only sdlc-core is required.

Artifacts & traceability

Every ID points back to the one before it, so you can follow any line of code back to the business need and any production incident back to the requirement it exposed.

US-1user story→ AC-1.2acceptance criterion→ ADR-001design decision→ T-3task→ TC-04test case→ PRpull request→ RCAincident

Other ID families: NFR-n non-functional requirements, BR-n business rules, DEF-n defects, and open issues prefixed with the phase (DIS-1, REQ-2, DES-1…).

sdlc_state.py trace parses these documents and prints the AC → task → test case → result matrix, plus every orphan: an AC without a task or test, a task without an AC, a failing or unrun test case, an open high-severity defect or review finding.

State script CLI

Skills call this script through run_py.sh. You can also run it directly to inspect a project. Path: plugins/sdlc-core/scripts/sdlc_state.py. Every per-feature command accepts --feature <slug>, and the default is the active feature.

CommandEffect

feature new "<Name>" [--type LANE] [--docs-root P] · feature list · feature switch <slug>Adds, lists and switches features (work items) in one project.
status [--json] [--all]Prints a table of phases with markers OK approved, ?? in review, .. draft, !! reopened, ~~ needs revalidation. It also shows stale approvals and the code-lock state.
next [--json]Returns the phase to work on, with its skills, agents, inputs, artifacts, gate, approver, open issues and the action to take.

approve <phase> --by N [--note T] [--accept-open-issues]The human gate. Requires in_review, a name and a human-intent token (or a terminal confirmation). Stores artifact hashes.
reopen <phase> --reason T [--by N]Sets the phase to reopened, adds the reason as an open issue, and marks later approved phases needs_revalidation.
verify [--json]Lists approved phases whose artifacts changed since approval. Exits 1 if any did.
trace [--json]Prints the AC → task → test case → result matrix and orphans.
metrics [--json]DORA metrics, plus per-phase cycle time, approval wait, review rounds and reopens.
record deploy|incident|restore [--note T] [--ref ID]Records delivery events for the DORA metrics.
settings show|add-code-path|remove-code-path|require-tests|add-test-pattern|remove-test-pattern|block-command|unblock-command|max-diff-linesTunes the gates. Changes that weaken a gate need a human token.
issue add <phase> "<question>"Records a decision only a person can make.
issue resolve <phase> <ID> --note "<decision>"Records the decision and timestamps the resolution.
phases [--json] · lanes [--json]Prints the process definition and the work-type lanes.

Extending

Change the process

The PHASES and LANES lists in sdlc_state.py are the machine-readable process. docs/process.md is the human-readable version, and the conductor's "phase contract" table is the fallback. tools/check_consistency.py (run in CI) fails when they drift apart, or when a skill or agent named in PHASES doesn't exist. Exit checks live in PHASE_TRACE_CHECKS and PHASE_HEADING_CHECKS.

Add a work type

Add an entry to LANES with its phase subset (kept in PHASES order) and a description, then add a row to the lanes table in docs/process.md.

Add a skill to a phase

Create plugins/<plugin>/skills/<name>/SKILL.md with name and description frontmatter, then add "<plugin>:<name>" to that phase's skills list so the conductor runs it in order. End the skill by handing back to sdlc-core:conductor.

Add a reviewer agent

Add plugins/<plugin>/agents/<name>.md with tools: Read, Grep, Glob (add Bash only for read-only git, tests and scanners, and say so in the prompt), and list it under the phase's agents. The conductor runs it as a subagent.

Add an eval

Create plugins/<plugin>/evals/<case>/prompt.md and graders/*.md (or run claude plugin eval init), then run claude plugin eval plugins/<plugin>.

Add a new plugin

Create plugins/<name>/.claude-plugin/plugin.json and add an entry to .claude-plugin/marketplace.json with name, source and description. Bump version when you ship changes.

Tune enforcement per project

code_paths, require_tests_on_commit, test_patterns, blocked_commands and max_diff_lines live in each project's state file. Change them with /sdlc-core:settings. Tightening works at any time. Weakening needs the human token.

Known limitations

These are behaviours of version 0.2.0 worth knowing before you depend on the gates.

AreaBehaviourEffect
Shell guardShell and PowerShell writes are parsed best-effort: redirects, common write commands, and inline scripts.It keeps a well-behaved agent on track, but it isn't a sandbox. A determined process can find another way to write a file. Approvals don't rely on it, because the state script checks the token itself.
Approval tokenThe token proves the user typed the slash command in this project within the last 30 minutes.It proves intent, not identity. The approver name is still whatever --by says, plus the recorded git identity. If your Claude Code build doesn't pass slash commands to UserPromptSubmit, approve from a terminal instead, where the script asks for confirmation.
Trace parsingIDs are read from markdown tables, headings and bullets with regular expressions.Artifacts that drift far from the templates can produce false gaps. Fix the artifact, or override with --force-reason, which the approver sees.
Stale detectionOnly artifact files are hashed.Code changed after the Build approval doesn't make Build stale. Review and the PR process cover code.
Code-path matchPaths are matched by prefix from the project root.Code outside the listed folders, such as root-level scripts or cmd/, isn't gated until you add it to code_paths.
Approver identityApproval records whatever name is passed to --by, plus how it was requested and the git identity.It's an audit trail, not authentication. Anyone at the keyboard can type the command.
