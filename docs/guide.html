Claude Code plugin marketplace · v0.1.0

Agentic SDLC Marketplace

A conductor plus ten phase plugins that take a feature from idea to deployment. Agents draft every phase. A named person approves each one before the next phase can start.

Marketplace name agentic-sdlc Repo rpino/agentic-sdlc-marketplace 11 plugins · 20 skills · 2 agents · 2 hooks Requires python3 (stdlib only) MIT

What it does

Claude Code is good at writing code, but on its own it will happily skip straight from a vague idea to an implementation. This marketplace puts a delivery process around it. Every feature passes through Discovery, Requirements, Design, Planning, Build, QA, Review, Release, Operate and Knowledge, in that order. Each phase produces a markdown artifact in docs/, and that artifact is the input to the next phase.

You drive the whole thing with four commands. The conductor works out which phase is current, runs that phase's skills, records questions that need a human answer, and then stops and waits for approval. Python hooks enforce the rules the prompts ask for, so an agent can't write production code before the plan is approved or edit the state file to approve itself.

Principles

AI drafts, humans decideEvery phase ends at a gate approved by a named person. The agent never approves.
Artifacts are the contractEach phase's output document is the next phase's input.
Traceability end to endUS → AC → design → task → test → PR → release → RCA.
Feedback loops are normalA later phase that finds a gap reopens the earlier phase instead of patching around it.
Lessons compoundAdopted retro lessons become standing rules in CLAUDE.md that every future agent follows.

The ten phases

Phases run strictly in order. Each one ends at a gate, shown as a diamond, with the role that must approve it. Select a phase to jump to its details.

1DiscoveryGATEProduct Owner 2RequirementsGATEProduct Owner 3DesignGATETech Lead 4PlanningGATETeam 5BuildGATETech Lead 6QAGATEQA Lead 7ReviewGATETech Lead 8ReleaseGATEProduct Owner 9OperateGATEProduct Owner 10KnowledgeGATETeam

Code paths unlock only after the Planning gate (phase 4) is approved. That is the hook-enforced line between thinking and building.

sdlc-core: the backbone

Every phase plugin depends on sdlc-core. It has three parts: a state machine that remembers where the project is, a conductor skill that runs the work, and hooks that enforce the rules.

The commands you use

CommandWho runs itWhat it does
/sdlc-core:init "Name" [approver]Person onlyCreates .sdlc/state.json, the docs/01…10 folders and a project CLAUDE.md, then starts Discovery right away.
/sdlc-core:next [notes]Person onlyRuns the next step of the current phase. If the phase is in_review and you add notes, they count as review feedback: the phase goes back to draft, gets revised, and is resubmitted.
/sdlc-core:approve [phase] [--note]Person onlyThe human gate. Shows an approval summary, confirms who is approving, records the approval, and names the next phase. It does not start that phase.
/sdlc-core:statusAnyoneShows every phase's status, who approved what, open issues, and who needs to act next.
/sdlc-core:reopen <phase> "reason"Person or agentSends work back to an earlier phase when a later one finds a gap, and records the gap as an open issue.

The conductor loop

The sdlc-core:conductor skill orchestrates. It doesn't do the phase work itself. It reads the state, routes to the right skills, and stops at the gate. next and init both hand off to it.

  1. Read state. Run sdlc_state.py next --json, which returns the phase, its status, its skills and agents, the expected artifacts, the gate, the approver and any open issues.
  2. Branch on status. in_review: stop and name the approver. reopened: ask for the missing decisions and resolve the issues. not_started or draft: continue.
  3. Mark in progress: set-status <phase> draft.
  4. Run the phase skills in order, feeding each one the previous phase's approved artifacts. Then run the reviewer agent, if the phase has one, and fold in its findings. If the phase plugin isn't installed, follow the built-in phase contract instead.
  5. Record human decisions as open issues (issue add). Scope, priority, business rules and risk acceptance belong to people.
  6. Submit for review: set-status <phase> in_review --artifact <path>.
  7. Stop and hand over in 3–6 lines: what was produced, where it is, open issues, who approves, and the exact /sdlc-core:approve command.

Hard rules in the conductor: one phase at a time, never approve, never edit the state file by hand, reopen instead of patching gaps, and every artifact references the IDs of the one before it.

Phase lifecycle

Every phase has one of five statuses. sdlc_state.py enforces each transition, so the agent can't jump straight to approved even if it tries.

RuleEnforced by
A phase can't move to draft or in_review until the previous phase is approved.set-status refuses
set-status only accepts draft and in_review. Approving and reopening have their own commands.set-status refuses
Only an in_review phase can be approved, and only with a non-empty --by NAME.approve refuses
Open issues block approval unless the approver passes --accept-open-issues.approve refuses
The current phase is always the earliest phase that isn't approved, so a reopened phase is automatically next. Downstream phases keep their status.next_phase()
Only a person moves a phase to approved.The conductor skill and disable-model-invocation on approve

Hooks & gates

Prompts ask the agent to follow the rules. Hooks make sure it does. Both hooks run only inside a project that has a .sdlc/state.json, found by walking up from the working directory. Everywhere else they do nothing.

EventScriptRule
SessionStart
startup · resume · clear · compact		sdlc_session.pyAdds the project name, current phase and status, and any open issues to Claude's context, along with an instruction to follow the conductor. Any session on any day knows where the project stands.
PreToolUse
Write · Edit · MultiEdit · NotebookEdit · Bash		sdlc_gate.pyState file is script-only. Denies Write/Edit on .sdlc/state.json, and Bash commands that mention it with >, tee, sed -i, mv, cp, rm or python -c unless they go through sdlc_state.py.
No code before a plan. Denies writes under settings.code_paths until planning is approved.
Default paths: src/ app/ lib/ services/ packages/ api/ web/ tests/ test/
Tests with every commit. On git commit, reads the staged files (plus unstaged files for -a) and denies the commit if code changed but no test file did.

A denial is returned as a permissionDecision: "deny" whose reason is prefixed [Agentic SDLC gate], so Claude sees why it was blocked and what to do instead.

Phase plugins

Each phase plugin is made of prompts: skills, an optional reviewer agent, and templates. Each skill also works on its own outside a managed project, for example /sdlc-review:pr-reviewer 142.

01

Discovery

sdlc-discovery

idea-interviewer

  • Asks one question at a time, about 8 at most: problem and evidence, who is affected, why now, outcome and metric, constraints, what's out of scope, risks and assumptions.
  • Doesn't propose solutions. This phase is only about the problem.
  • Writes "Unknown — open question" instead of inventing facts. The brief stays to one page.
Input
The raw idea
Output
docs/01-discovery/problem-brief.md
Gate · Product Owner and stakeholder agree the problem is worth solving.
02

Requirements

sdlc-requirements

spec-writer → acceptance-criteria → requirements-reviewer

  • spec-writer: user stories US-n (INVEST, Must/Should/Could), measurable NFR-n, business rules BR-n, out of scope, open questions. Avoids solution language and vague words.
  • acceptance-criteria: AC-n.m in EARS form (WHEN / WHILE / IF … THEN / WHERE … THE SYSTEM SHALL …; Gherkin is also accepted). A coverage checklist covers the happy path, validation, permissions, state conflicts, dependency errors, user-visible messages and audit. Ends with a traceability table.
  • requirements-reviewer (read-only agent): looks for ambiguity, missing edge cases, untestable criteria, scope creep and missing business rules.
Input
Approved problem brief
Output
docs/02-requirements/requirements.md
Gate · Product Owner approves the stories and testable acceptance criteria.
03

Design

sdlc-design

design-drafter → design-reviewer

  • Reads the real codebase before proposing anything. Covers components, data model, APIs, sequence flows, edge cases, and a map from each AC to the design element that satisfies it.
  • Writes ADRs for significant decisions.
  • design-reviewer (read-only agent) challenges integration assumptions, data-model risks, failure modes, security, scalability, over-engineering and requirement coverage.
Input
Approved requirements
Output
docs/03-design/design.md, adr/ADR-nnn-*.md
Gate · Tech Lead approves the design and ADRs.
04

Planning

sdlc-planning

task-breakdown

  • Tasks T-n that are small (one PR, about a day or less), vertical, traceable to AC IDs, verifiable with their own definition of done, and ordered with depends on links.
  • Adds cross-cutting tasks the design implies: migrations, feature flag, telemetry, docs, config. Groups tasks into milestones and estimates them; the estimates are marked as the agent's guesses.
  • A coverage check confirms every AC has at least one task. Creating Jira, Linear or Azure DevOps tickets is optional and only happens if you ask.
Input
Requirements and design
Output
docs/04-planning/tasks.md
Gate · The team agrees tasks, sequence and priorities. Approving this gate unlocks the code paths.
05

Build

sdlc-build

task-executor (one task at a time)

  • Reads the task, its ACs and the relevant design sections, plus the code it will touch and the CLAUDE.md standing rules. Works on a feature/<task-id>-<slug> branch.
  • Test first: writes failing tests named after ACs (test_ac_1_2_…), makes the smallest change that passes, runs the suite and linters, then reviews its own diff.
  • Commits as T-3: … (AC-1.1, AC-1.2), opens a PR, updates tasks.md and the build log, then stops so a developer can review.
  • If the design or an AC turns out to be wrong, it reopens that phase instead of improvising.
Input
Approved tasks
Output
Code, tests, PRs, docs/05-build/build-log.md
Gate · Tech Lead confirms every task diff has been reviewed and all tasks are done.
06

QA

sdlc-qa

qa-from-acceptance-criteria

  • Writes at least one TC-n per AC, with negative and boundary cases (limits ±1, empty, duplicates, concurrency, time zones).
  • Does an exploratory pass as a real user and as a malicious one. Automates missing tests in the project's own framework, runs the suite, and logs defects DEF-n.
  • Gaps go back upstream: it reopens Requirements instead of inventing the rule. It also flags false greens, meaning tests that assert nothing or mock the thing under test.
Input
Requirements, design, built code
Output
docs/06-qa/test-cases.md, test-report.md
Gate · QA Lead confirms every AC has a passing test.
07

Review

sdlc-review

pr-reviewer → security-checklist

  • pr-reviewer: first-pass review of each PR against its task, ACs and design: correctness, tests, readability, conventions, performance and risk, ranked by severity.
  • security-checklist: 11 items based on OWASP and ASVS (access control and IDOR, auth, input validation, injection, secrets, PII, dependencies, error handling, audit logging, abuse cases, configuration). Each item gets Pass, Fail or N/A with file:line evidence.
  • Any Critical or High finding must be fixed, or risk-accepted by a named person.
Input
Pull requests
Output
docs/07-review/review-report.md
Gate · Tech Lead signs off the merge with no open high-severity findings.
08

Release

sdlc-release

release-notes (+ pipeline-fixer)

  • release-notes: a release plan (feature flag, staged rollout, monitoring, rollback, go/no-go checklist) and release notes for three audiences: business users, support staff and engineers.
  • pipeline-fixer: reads CI/CD logs, sorts the root cause into code, flaky test, environment, config or dependency, and proposes the smallest fix. It is also useful on its own.
Input
Approved build
Output
docs/08-release/release-plan.md, release-notes.md
Gate · Product Owner and stakeholder give go/no-go.
09

Operate

sdlc-ops

incident-summarizer

  • Health check mode: a post-release monitoring summary.
  • Incident mode: a blameless RCA with timeline, impact, root cause from 5 whys, the fix, and follow-ups. Follow-ups include new acceptance criteria that go back into Requirements, and candidate standing rules.
Input
The live system
Output
docs/09-operate/monitoring.md, RCA-*.md
Gate · Product Owner confirms the rollout is stable or incidents are handled.
10

Knowledge

sdlc-knowledge

retro-capture → knowledge-updater

  • retro-capture: gathers evidence from the state history first. It computes cycle time per phase, the number of feedback loops, gaps caught before production, escaped defects, and an AI catch rate. Then it runs the retro and proposes concrete, checkable rules.
  • knowledge-updater: writes only the rules the team adopted into CLAUDE.md's "Standing rules" section. It removes duplicates and cites the source, for example (RCA-2026-031). It can also draft improvements to the marketplace's own skills for you to review.
Input
Everything from the run
Output
docs/10-knowledge/retro.md, CLAUDE.md
Gate · The team agrees which lessons become standing rules.

Rolling out gradually: if a phase plugin isn't installed, the conductor does that phase itself using the built-in "phase contract" table in its skill, and suggests installing the plugin for more consistent results. Only sdlc-core is required.

Artifacts & traceability

Every ID points back to the one before it, so you can follow any line of code back to the business need and any production incident back to the requirement it exposed.

US-1user story→ AC-1.2acceptance criterion→ ADR-001design decision→ T-3task→ TC-04test case→ PRpull request→ RCAincident

Other ID families: NFR-n non-functional requirements, BR-n business rules, DEF-n defects, and open issues prefixed with the phase (DIS-1, REQ-2, DES-1…).

The state file

.sdlc/state.json is the process's memory. sdlc_state.py writes it atomically (to a temp file, then os.replace) and appends every change to history. Here is an abbreviated example from partway through a run:

  "schema_version": 1,
  "project": "Membership Freeze",
  "slug": "membership-freeze",
  "approvers": { "product_owner": "Tito", "tech_lead": "Tito", "qa_lead": "Tito", "team": "Tito" },
  "settings": {
    "code_paths": ["src/", "app/", "lib/", "services/", "packages/", "api/", "web/", "tests/", "test/"],
    "require_tests_on_commit": true,
    "test_markers": ["test", "spec", "__tests__"]
  },
  "current_phase": "requirements",
  "phases": {
    "discovery": { "status": "approved", "artifacts": ["docs/01-discovery/problem-brief.md"],
                   "approved_by": "Tito", "approved_on": "2026-10-01", "open_issues": [] },
    "requirements": { "status": "in_review", "artifacts": ["docs/02-requirements/requirements.md"],
                      "approved_by": null, "approved_on": null,
                      "open_issues": [{ "id": "REQ-1", "text": "Check-in while frozen?",
                                        "raised": "2026-10-01", "resolved": false }] },
    "design": { "status": "not_started", … }
    // … planning through knowledge
  },
  "history": [
    { "ts": "…", "event": "project_created", "by": "Tito", "note": "Membership Freeze" },
    { "ts": "…", "event": "approved", "phase": "discovery", "by": "Tito" },
    { "ts": "…", "event": "issue_added", "phase": "requirements", "note": "REQ-1: Check-in while frozen?" }

}

Approver names default to the Product Owner given at init. Tech Lead and QA Lead can be set separately with --tech-lead and --qa-lead. The phase definitions themselves (skills, artifacts, gate text, approver role) live in the PHASES list at the top of sdlc_state.py, not in the state file.

State script CLI

Skills call this script. You can also run it directly to inspect a project. Path: plugins/sdlc-core/scripts/sdlc_state.py.

CommandEffect
init "<Name>" --approver N [--tech-lead N] [--qa-lead N] [--dir P]Creates the state file, the docs/ phase folders and CLAUDE.md. If a CLAUDE.md already exists, the SDLC section is appended to it.
status [--json]Prints a table of phases with markers OK approved, ?? in review, .. draft, !! reopened.
next [--json]Returns the phase to work on, with its skills, agents, artifacts, gate, approver, open issues and the action to take.
set-status <phase> draft|in_review [--artifact P]…Moves a phase forward. Refuses if the previous phase isn't approved.
approve <phase> --by N [--note T] [--accept-open-issues]The human gate. Requires in_review and a name.
reopen <phase> --reason T [--by N]Sets the phase to reopened and adds the reason as an open issue.
issue add <phase> "<question>"Records a decision only a person can make.
issue resolve <phase> <ID> --note "<decision>"Records the decision and timestamps the resolution.
phases [--json]Prints the process definition.

/plugin marketplace add rpino/agentic-sdlc-marketplace
/plugin install sdlc-core@agentic-sdlc

Updating the marketplace

Edit the files in the repo, commit and push, then run /plugin marketplace update agentic-sdlc in Claude Code. To try changes before pushing, add the local folder instead: /plugin marketplace add ./agentic-sdlc-marketplace.

Extending

Change the process

The PHASES list in sdlc_state.py is the machine-readable process. docs/process.md is the human-readable version, and the conductor's "phase contract" table is the fallback. Keep all three in sync when you add, remove or reorder a phase.

Add a skill to a phase

Create plugins/<plugin>/skills/<name>/SKILL.md with name and description frontmatter, then add "<plugin>:<name>" to that phase's skills list so the conductor runs it in order. End the skill by handing back to sdlc-core:conductor.

Add a reviewer agent

Add plugins/<plugin>/agents/<name>.md with tools: Read, Grep, Glob so it can only read, and list it under the phase's agents.

Add a new plugin

Create plugins/<name>/.claude-plugin/plugin.json and add an entry to .claude-plugin/marketplace.json with name, source and description. Bump version when you ship changes.

Tune enforcement per project

settings.code_paths, settings.test_markers and settings.require_tests_on_commit live in each project's state file. Because the hook blocks direct edits, change them through the script, or extend the script with a settings command.

Roadmap

  • Connectors (.mcp.json) for Jira and GitHub in Planning, Build and Review
  • Evals for each skill
  • Configurable phase sets, such as a "lite" path for small changes

Known limitations

These are behaviours of version 0.1.0 worth knowing before you depend on the gates.

AreaBehaviourEffect
Python launcherHooks and skills call python3.On Windows, python3 is sometimes only the Microsoft Store stub, and the hooks fail if it is. Check with python3 --version.
Test detectionA file counts as a test if its path contains test, spec or __tests__ anywhere.src/contest.ts or specials.py would satisfy the test-with-commit rule.
Shell guardShell writes to the state file are caught with a regex for common write commands.Fine for keeping a well-behaved agent on track, but not a security boundary.
Code-path matchPaths are matched by prefix from the project root.Code outside the listed folders, such as root-level scripts or cmd/, isn't gated until you add it to code_paths.
Approver identityApproval records whatever name is passed to --by.It's an audit trail, not authentication. Anyone at the keyboard can type the command.
SettingsThere's no CLI command to change settings.Tuning enforcement for a project currently means extending the script.
